# GNET School Management System — AWS Lightsail Deployment Audit

Review date: 11 October 2026 · Scope: deployment, security, database, backups, monitoring, and budget

My recommendation is to hold off on deploying the current plan to production. The documents contain useful engineering practices, but several deployment instructions conflict with each other or could cause the application to fail, expose sensitive services, or lose school records.

The good news is that you do not necessarily need an expensive AWS architecture. With your 2026 AWS credits and the additional $100 you are willing to spend, we can aim for a lean initial deployment, provided we select the right Lightsail option and validate the application's resource requirements first.

I reviewed the six documents you uploaded, including the deployment plan and its backup copy, API security guidelines, database migration guide, disaster recovery plan, and monitoring guide. The two deployment-plan files also contain differing workflow instructions, so we should establish one authoritative version rather than follow both.

## 5. Critical corrections required in the deployment plan

These are the changes I would make before creating the production instance.

1\. Replace the Lightsail deployment workflow

The documented `aws-actions/amazon-lightsail-deploy-image@v1` approach targets Lightsail container services, not an ordinary Linux instance running Docker Compose. The workflow also refers to `gnet-sms:latest`, although the build steps publish separate service images.

Fix: build each image, tag it with the Git commit SHA, push it to a registry, and deploy to the Linux instance using a controlled SSH-based deployment script or a similarly secured deployment mechanism. The script should pull the intended image versions and run `docker compose up -d` using the correct Compose file.

2\. Remove default production credentials

The Compose example uses `sms` / `sms` for PostgreSQL and example MinIO credentials such as `smsminio-secret`. These are demonstration values, not production secrets.

Fix: generate strong unique credentials, use a dedicated database role per service with least privilege, and ensure the `postgres` container is not published to the internet. Keep production secrets outside Git, and do not include `.env.production` in the repository or backups that lack appropriate encryption and access controls.

3\. Correct exposed ports and external URLs

The example publishes Redis port `6379` and MinIO ports `9000` and `9001`. The example also sets `S3_PUBLIC_URL=http://localhost:9000`.

Fix: keep PostgreSQL, Redis, MinIO's API, and MinIO's console private on the Docker network. Expose only the reverse proxy's HTTP/HTTPS ports. `localhost` in a browser refers to the visitor's own computer, not your server, so externally accessed file URLs must use a valid public HTTPS hostname or an appropriately designed presigned-upload/download flow.

4\. Make database migrations an explicit deployment stage

The plan says migrations should run after startup in some places and as part of the GitHub Actions deployment in others.

Fix: build and test images first, take a verified backup, run the approved Prisma production migrations exactly once, then deploy compatible application versions and run smoke tests. Do not run schema migrations independently from every application replica or blindly roll back a schema when application rollback occurs.

5\. Fix the backup architecture

The disaster-recovery plan puts PostgreSQL backups in a MinIO bucket on the same system. If the instance or its storage is lost, both the live files and backups may disappear together.

Fix: maintain encrypted, verified backups outside the production instance and outside the only live MinIO storage location. Amazon S3 is one possible destination if the account's credit terms and storage costs make it suitable. Keep separate database dumps and object-storage backups, and perform actual restore tests.

## 7. Disaster recovery: the current targets are too optimistic

Your recovery plan claims a database restore can typically take 2–5 minutes and a complete disaster recovery can take 45–60 minutes. Those are targets or estimates, not verified results.

There are also inconsistencies:

- A daily database backup at 02:00 UTC can leave nearly 24 hours of transactions exposed to loss, not guarantee an RPO below four hours.
- Some restore commands reference a database named `sms`, while the documented production database is `sms_db`.
- Several MinIO restoration examples use bucket operations and archive commands that need verification against the actual `mc` version and backup format.
- A database restore alone is not enough: database records and uploaded documents must correspond to the same recovery point.
- The sample procedures include destructive commands such as removing a live bucket or dropping a database. Those must never be run against production without a verified backup, explicit target confirmation, and a tested recovery procedure.

My recommendation: start with daily encrypted database backups, daily object-storage backups or synchronization to an independent destination, a retention policy, and a documented restore test. If losing a full school day of changes is unacceptable, add more frequent database backups or point-in-time recovery once the budget and storage architecture are confirmed.

## 8. Security audit: important issues beyond deployment

The security guide has good intentions, but several recommendations need tightening before this system handles real student and financial data.

JWT and internal service authentication

The guide describes HS256 JWTs, a shared `INTERNAL_SERVICE_TOKEN`, and refresh tokens that are not yet implemented. A shared token across services increases the impact of a leak.

Generate independent production secrets, validate token issuer/audience and expiry, implement secure refresh-token rotation if required, and ensure internal endpoints cannot be accessed by bypassing the gateway. Consider per-service credentials where practical.

File uploads and MinIO

The guide correctly identifies MIME validation and file-size restrictions, but a client-supplied MIME type is not proof of file content. Validate file signatures, enforce size limits on the actual upload, use short-lived presigned URLs, and scan untrusted files before making them available.

CORS and rate limiting

The example uses a wildcard MinIO CORS origin. Replace it with explicit permitted origins and methods appropriate to the application. Login rate limits and IP-blocking rules must be implemented and tested; listing them in a document does not activate them automatically.

Secret handling and access control

The documents sometimes say configuration is stored in Git and elsewhere say secrets must never be committed. These instructions conflict. Store only non-secret templates in Git, keep real secrets in GitHub Actions secrets or an appropriate secrets manager, and never log credentials or tokens.

Also correct the operational examples before using them:

- The documented SSH hostname and username are placeholders and do not constitute a working connection command.
- Verify the Docker Compose installation instructions for the chosen Ubuntu release; the package name `v2-plugin` should not be assumed to be valid.
- The sample Caddy configuration must use the actual application hostname and the correct Docker service name or network address. `localhost` inside a container normally means that same container.
- Check every public port in the final Compose configuration, not just the Lightsail firewall. A Docker port publication can create exposure that differs from what you intended.
- The monitoring guide's sample dashboard values, including the example memory and storage readings, should be treated as illustrations, not measured production results.

## 9. Monitoring: start small and verify what actually works

Your monitoring document proposes Prometheus, Grafana, alerting, tracing, log aggregation, and numerous custom metrics. That is more infrastructure to maintain and pay for than I would introduce during your first deployment.

Start with:

1. Lightsail's built-in instance metrics for CPU, network traffic, and server health.
2. Docker Compose health checks, restart policies, and log rotation.
3. A working `/health/live` endpoint for process health and `/health/ready` for readiness, including relevant database dependencies.
4. Automated alerts for service downtime, low disk space, high memory use, and failed or stale backups.
5. A documented manual check that verifies login, tenant isolation, student records, fee receipts, uploads, and report generation.

Only add a full metrics and logging stack after confirming the application runs reliably and the server has enough headroom. Metrics endpoints should be private or appropriately authenticated; don't expose them publicly just to make a monitoring dashboard work.
